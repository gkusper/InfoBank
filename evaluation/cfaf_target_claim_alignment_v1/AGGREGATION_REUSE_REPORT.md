# Deterministic aggregation reuse feasibility

Source: `backend_python/aggregate_executor.py` and its tests at `8079f29dc3a97273f51b55b2a22f9ff896a2e758`. The module's only non-stdlib execution dependency for the core is the relevance module's policy-label constants. After inspecting the entire small executor and its tests, selected dataclasses/constants/functions were extracted into `vendor/aggregate_core.py`; the production routing/database integration was not imported.

Reused core: `AggregateConfig`, `AggregateContribution`, `_public_refusal` and `execute_aggregate`. It filters FULL/AGGREGATE permissions, deterministically deduplicates contributor IDs, rejects nonfinite contributions and computes COUNT/SUM/MEAN after a configurable minimum contributor threshold. `extract_unambiguous_numeric_value` was deliberately not reused: the task requires structured authorized numeric contributions rather than guessed individual values in prose.

`aggregate_smoke_adapter.execute` is a small isolated adapter. It accepts typed numeric records and the existing CFAF permission classes, filters denied/metadata-only records before reading their value, validates k as an integer >=2, delegates computation to the inspected core and releases only operation/value. Individual identifiers, input values, duplicate rows and contributor counts are absent from generator context, citations and public trace. COUNT releases its requested count value. Below-threshold output is identical for an empty input and one permitted contributor plus denied data.

Synthetic authorized contributions 17, 31 and 46, with a duplicate and denied input, produce COUNT=3, SUM=94 and MEAN=31.333333. The smoke results and privacy checks are in `aggregation_smoke_results.json` and the controlled test suite. No model call was used. These are internal development tests, separate from RefusalBench classification and not independent privacy validation.

This is not a production aggregation subsystem and does not change the experimental permission model. Production integration would require a trusted contribution schema containing metric, unit, period and contributor identity; policy-engine decisions bound to the current user/purpose; an explicit metric/operation request contract; audit/storage retention rules; and a policy-approved aggregate-release interface. The existing generator projection should accept only the sanitized aggregate result, not raw individual records. The smoke adapter is retained as an implementation prototype and feasibility result, not wired into the measured CFAF gate.
