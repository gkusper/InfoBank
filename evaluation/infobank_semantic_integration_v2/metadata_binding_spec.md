# Metadata binding v2 specification

The previous fixture retrieval interface supplied ranked sources but no authoritative entity-to-view assertion. Being the sole retrieved document was insufficient evidence of association. The extension resolves the query's candidate target against an internal source catalogue AFTER access projection. Explicit retrieval_aliases are the preferred index interface. For legacy fixtures, the adapter uses the ordinary source title as a private searchable catalogue label. It performs a whole-target phrase match, requires exactly one authorized match, and uses neither IDs nor benchmark semantic annotations to determine association. Private titles, aliases, opaque original IDs and match counts are never sent to models.

Only included PUBLIC permitted views participate. A unique match yields {source_id: neutral-view-id, binding_status: TRUSTED_QUERY_TARGET}; unresolved/ambiguous permitted views carry only their respective status. Hidden/DENY entries yield no view or binding and do not change visible match cardinality. A single result with an unmatched name remains unresolved. The internal audit records resolver version, query hash, policy snapshot and neutral matched view IDs. It is not a model-visible payload.

The request-bound guard rechecks query-only profiling, current policy, permitted content and catalogue resolution before every external call. Any policy, whitelist, source content or target change invalidates the old assertion; mutation or forged bindings is rejected. This is an in-process trust boundary, not a cryptographic authentication protocol or a production multi-principal retrieval service.

Binding establishes association only. Metadata FULL additionally needs all requested fields in the whitelist/permitted values, sufficient primary evidence and verified spans. Missing/unauthorized fields, unknown target, multiple target matches and body-content requests remain restricted. No filename/title is smuggled into the metadata context to make a FULL case pass. All evidence offsets and hashes still refer to the original permitted JSON metadata view, not private catalogue text.

Limitations: exact lexical target resolution, truthful local catalogue assumptions and bounded target extraction. Production integration should provide authenticated principal-scoped resource selection and explicit aliases from its real retrieval system. Fuzzy matching or simply choosing the first result would require separate validation and is not implemented here.
