# Query profile v2 specification

The profiler accepts only the actual question string. Its API accepts no source list, access mode, case identifier or benchmark labels. A conservative English grammar emits explicit requirements: AGGREGATE_COUNT, AGGREGATE_SUM, AGGREGATE_AVERAGE, AGGREGATE_OTHER, INDIVIDUAL_RECORD, METADATA_LOOKUP, DOCUMENT_CONTENT, ACTION_LOOKUP or UNRESOLVED. Requirements are a list, so a request for both individual records and a statistic retains both obligations. An adjective such as 'individual' inside a count/sum question does not itself request record disclosure.

Metadata aliases map to explicit field names (file_type, created_at, modified_at, author, owner, size_bytes). Asking for unspecified metadata leaves resolution unresolved. Unknown output forms remain UNRESOLVED. A separately extracted query target is a candidate search phrase, not an assertion that a matching source exists. The grammar is deliberately bounded English support, not general natural-language understanding.

The profiler runs before candidate retrieval in the eight-stage adapter. Its output is shared with both generated systems. The semantic analyzer evaluates support for each named requirement using permitted spans; it does not produce or override request_scope. The sufficiency stage requires every requirement, authorized scope, appropriate primary support, a grounded candidate, valid metadata binding and requested fields before feeding the unchanged top-level selector. A count alone does not supply an average; the semantic support assessment must identify the missing statistic. The query profiler never computes a final mode or answer.

All deterministic synthetic results measure query parsing and governed plumbing under controlled upstream semantic assessments. They do not measure LLM accuracy or independent generalization. Functional tests cover positive and negative paraphrases, mixed requests, ambiguous scopes and count-versus-individual near controls.
